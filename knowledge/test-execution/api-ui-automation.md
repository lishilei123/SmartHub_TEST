# API / UI 自动化执行经验

本文件用于测试执行实现，不用于改变正式 TestCase 的业务语义。

## KE-API-001 测试数据隔离

创建资源时使用本次 Run 唯一数据，例如随机后缀或时间戳；后续请求始终从创建响应中提取 ID，不硬编码数据库 ID。

执行结束后清理本用例创建的数据。若用例目标本身是删除/级联删除，则由验证步骤承担清理结果确认。

## KE-API-002 鉴权处理

需要鉴权的 API 用例统一从登录步骤取得 Token，并显式设置 Authorization Header。负向鉴权用例必须独立执行，不能复用已经自动注入的合法 Header。

## KE-API-003 业务断言优先

不要把 `status == 200` 当作唯一成功条件。根据正式 TestCase 继续断言：
- 返回字段
- 列表实际成员
- 状态变化
- 数据是否持久化
- 错误码/错误信息（仅当正式规则明确）

## KE-UI-001 稳定定位器

UI 自动化优先使用稳定的可访问语义，例如 role、label、可见文本或明确 data-testid。避免依赖动态序号、随机 class 或数据库 ID。

## KE-UI-002 二次确认

当正式需求声明删除需要确认时，UI 用例要把“出现确认交互”和“确认后真实删除”拆成两个观察点；不能只点击删除后检查列表消失。

## KE-UI-003 UI/API 交叉校验

对于关键写操作，可以在 UI 操作后使用 API 查询验证后端真实状态，减少仅凭页面缓存或前端局部状态误判。

## KE-EXEC-001 知识不可覆盖正式用例

执行知识只允许帮助选择 locator、准备数据、组织请求和稳定校验。若知识内容与冻结 TestCase、Requirement Release 或 TestExecutionHandoff 冲突，以正式冻结输入为准，不得修改 Expected Result 让脚本通过。
