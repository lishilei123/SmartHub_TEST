# CRUD、状态机与数据一致性测试场景

## KS-CRUD-001 CRUD 完整闭环

对于典型资源管理需求，测试不应只验证“接口返回成功”，而应形成完整闭环：

```text
Create → Read → Update → Read → Delete → Read/Query
```

每一步都验证持久化后的真实状态，而不是只相信上一请求的响应体。

## KS-CRUD-002 父子资源删除

当父资源和子资源存在关联且需求声明级联删除时：
1. 先创建父资源。
2. 创建至少一个关联子资源。
3. 删除父资源。
4. 从子资源查询入口再次验证子资源已经不存在。
5. 同时验证列表、统计等派生数据没有残留。

只验证父资源删除成功不足以证明级联删除正确。

## KS-STATE-001 状态图正向路径

需求给出状态流转图时，每条合法边都应独立覆盖。例如：

```text
A → B
B → C
```

不能只覆盖一次 `A → B → C` 长链路，因为这样难以定位单条边失败。

## KS-STATE-002 非法状态边

除了合法边，还应系统性检查：
- 跳级
- 回退
- 已终态继续修改
- 重复提交当前状态

正式 Expected Result 必须以当前需求为准；知识库只提示“哪些边值得检查”，不得自行发明新的业务状态规则。

## KS-DATA-001 跨入口一致性

资源状态发生变化后，至少检查一个关联入口，例如：
- 详情 vs 列表
- 列表 vs Dashboard
- API vs UI
- 删除结果 vs 搜索结果

避免单接口正确、系统整体数据不一致。
